# แผนทดสอบความสนุก

สถานะ: เกณฑ์ทดลองที่เสนอ ไม่ใช่ผลวัดหรือมาตรฐานอุตสาหกรรม

## คำถามหลัก
ผู้เล่นเริ่มรอบสองด้วยความอยากเล่นเองหรือไม่ และอธิบายได้ไหมว่ารอบถัดไปจะเปลี่ยนอะไร?

## วิธีทดสอบ
เริ่ม 5 คนที่ไม่เคยเล่น ให้เข้าเกมโดยไม่อธิบายล่วงหน้า สังเกต 10–15 นาที ไม่ชี้นำการเลือก Build แล้วค่อยถาม หากมีปัญหาพื้นฐานให้แก้ก่อนทดสอบ 20–30 คน เก็บรุ่นเครื่อง รูปแบบจอ และวิธีควบคุมเพื่อแยกปัญหามือถือกับคอม

หลังเล่นถาม: ช่วงไหนสนุกที่สุด? แพ้เพราะอะไร? การ์ดไหนเปลี่ยนการเล่น? ถ้าเล่นอีกจะลองอะไร? มีช่วงไหนรู้สึกว่าแค่รอ?
ไม่ใช้คำชมภาพแทนหลักฐานความสนุก และไม่ถือว่ากลุ่มเล็กยืนยัน retention ของตลาดได้

## Event ที่ต้องมีเมื่อพัฒนา
| Event | ข้อมูลขั้นต่ำ |
|---|---|
| play_ready | session ไม่ระบุตัวบุคคล, รุ่น build, ประเภทจอ/การควบคุม |
| run_start | run_id, ลำดับรอบใน session |
| first_move / first_kill | เวลาเล่นนับจาก run_start |
| upgrade_offered / upgrade_chosen | เวลาเล่น, ชุดตัวเลือก, สิ่งที่เลือก |
| evolution_unlocked | สูตร, เวลาเล่น |
| damage_taken / death | แหล่งความเสียหาย, เวลาเล่น |
| boss_start / boss_end | เวลาเล่น, ชนะหรือไม่ |
| run_end | ชนะ/ตาย/หมดเวลา/ออก, เวลาเล่น, Build |

event จบรอบต้องเกิดครั้งเดียวต่อ run_id; ปิดแท็บให้ถือว่าออกเมื่อ session ขาดช่วงตามนิยามที่ระบุในรายงาน อย่านับเป็นผู้ชนะหรือเงียบหายจากตัวหาร
แยกเวลาโหลด เวลาเล่นจริง และเวลาคิดเลือกการ์ด ห้ามเก็บชื่อ/ข้อความส่วนตัวเพื่อวัด gameplay

## เกณฑ์ตัดสินใจ Combat Slice
- เริ่มเล่นได้ใน 10 วินาทีหลัง play_ready และเลือกอัปเกรดแรกภายใน 30 วินาทีของการเล่นจริง
- รอบจบภายใน 5 นาทีของเวลาเล่นจริง ไม่รวม Pause/เลือกการ์ด
- อย่างน้อย 60% อยู่เล่นจนถึง 5 นาทีหลังเริ่มรอบแรก รวมผู้ที่แพ้แล้วเริ่มใหม่; รายงานคู่กับเวลาที่เล่นจริงและอัตราจบรอบ เพื่อไม่ให้การหยุดนับเป็น engagement
- อย่างน้อย 40% เริ่มรอบสอง โดยตัวหารคือทุกคนที่เริ่มรอบแรก ไม่ใช่เฉพาะผู้ชนะ
- ผู้เล่นส่วนใหญ่บอกความต่างของ Build สองสายได้ และเข้าใจสาเหตุแพ้ได้จากการสังเกต/สัมภาษณ์
- ทดสอบรอบเต็มบนมือถือเป้าหมาย: ตั้งเป้า 30 FPS อย่างน้อย 95% ของเฟรมระหว่างเล่น, ไม่มี crash และไม่มีอาการหน่วงจนหลบไม่ได้; เก็บ p95 frame time, peak enemies และจำนวน particle ประกอบ

รายงานจำนวนจริงควบคู่เปอร์เซ็นต์ เช่น 8/20 ไม่สรุปว่าผ่านจากการทดสอบผู้พัฒนาเอง
ถ้าไม่ผ่าน ให้แก้จังหวะต่อสู้ การอ่านภัย การเลือก Build และเวลารอ แล้วทดสอบรอบใหม่ก่อนเพิ่ม Idle/ร้านค้า

## Retention ระยะถัดไป
เมื่อมีระบบกลับมาเล่นและ consent/วิธีระบุผู้ทดลองที่เหมาะสม ค่อยวัด D1 >=30% และ D7 >=10% เป็นสมมติฐานจาก GDD
กำหนด cohort ด้วยวันเริ่มเล่นครั้งแรกใน Asia/Bangkok; D1 คือกลับมาเริ่มรอบในวันปฏิทินถัดไป D7 คือวันที่เจ็ด รายงานเฉพาะ cohort ที่รอครบแล้ว พร้อมจำนวนคนและนิยามเดิมทุกครั้ง
ไม่ตีความการเปิดหน้าเพื่อรับของอย่างเดียวเป็นการกลับมาเล่นรอบใหม่
